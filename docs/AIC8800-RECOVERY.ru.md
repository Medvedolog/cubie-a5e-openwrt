# Cubie A5E: ручное восстановление AIC8800D80 по SDIO

**Экспериментальная функция.** Перенесена архитектура из
[`opiz3-wlan-backport`](https://github.com/Medvedolog/opiz3-wlan-backport/blob/main/package/kernel/uwe5622/files/uwe5622-recover),
но механизм пока **не проверен на железе Cubie A5E**. Автоматического
watchdog, hotplug-trigger и повторного сброса при каждой ошибке здесь **нет**.

## Назначение

Когда AIC8800D80 обнаруживается на SDIO, но `aic8800_fdrv` не может
загрузить firmware (в логе `sunxi-mmc 4021000.mmc: data error`,
`aicwf_sdio_send_pkt fail-110` и отсутствует `phy*`), попробуйте
ручное восстановление без перезагрузки платы:

1. Запомнить физический Wi-Fi host `4021000.mmc` независимо от номера `mmcN`.
2. Остановить **только** его радиоинтерфейсы через netifd.
3. Выгрузить `aic8800_fdrv`, затем `aic8800_bsp`. При отказе выгрузки
   **не отключать** SDIO-контроллер.
4. Выполнить sysfs `unbind` → `bind` ровно для `4021000.mmc`.
5. Дождаться повторного появления SDIO, загрузить драйверы, дождаться PHY.
6. Если первая загрузка ранее не закончила `uci-defaults`, повторить их.
7. Поднять только радио этого контроллера; сетевой reload — исключительно
   при необходимости, когда netifd ещё не знает новое радио.

Во избежание бесконечного цикла: `mkdir`-lock и максимум **3 попытки
за 1800 секунд**, счётчик — только во временной RAM (`/tmp`).
Скрипт не меняет исходники драйвера и не включается автоматически.

## Безопасность и ограничения

- **Первый запуск делать по UART или по проводному Ethernet, не по Wi-Fi.**
  Подключение через AIC8800 будет прервано.
- Контроллер системной SD-карты на A5E — `4020000.mmc`; скрипт
  отказывается работать, если на целевом `4021000.mmc` найдены блоковые
  устройства. Нужен работающий DT `mmc-pwrseq`.
- `rmmod` может заблокироваться в ядре. После тайм-аута 20 секунд
  сброс SDIO **не выполняется**, чтобы не отключать контроллер, пока
  драйвер остаётся активен.
- Не проверено, проходит ли `unbind/bind` контроллера `sunxi-mmc`
  полностью и повторяет ли `mmc-pwrseq` GPIO `WL_REG_ON` (PM1). Нужен
  первый аппаратный тест и журнал.
- Текущий патч DTS задаёт `max-frequency=35000000`: фактически SDIO
  после удачного запуска работал на 33,33 МГц. Recovery не меняет частоту.
- Команда `--run` разрывает работающие Wi-Fi-соединения. Не используйте
  её в промышленном роутере без запасного канала управления.

## Тест на плате

Сначала убедиться, что образ содержит файл
`/usr/sbin/aic8800-recover`. В сборочном workflow он устанавливается
с правами `0755`.

```sh
aic8800-recover --check
cat /proc/mounts | grep -E ' / |mmcblk'
dmesg | grep -Ei 'aic|sdio|4021000|mmc-pwrseq' | tail -80
```

Если preflight успешно проходит и связь с платой идёт по проводному
каналу, вручную:

```sh
aic8800-recover --run
logread -e aic8800-recover
dmesg | grep -Ei 'aic|sdio|4021000|mmc-pwrseq|timeout' | tail -100
iw dev
wifi status
uci -q show wireless
```

При успехе проверьте, появился ли PHY и запустился ли AP. Сообщение
`recovery completed` подтверждает возврат PHY и отправку команд netifd,
**но само по себе не подтверждает реальную передачу трафика**. Подключите
клиента и проверьте DHCP/iperf3.

### Критерии испытания

- При сбое firmware `-110`: recovery возвращает PHY без `reboot`.
- Номера `mmc0/mmc1`, `phy0/phy1`, `radio0/radio1` не зашиты в
  скрипт. Физический контроллер идентифицируется адресом `4021000.mmc`.
- Системная microSD и проводная сеть не перезагружаются.
- Повторные старты не создают лишних UCI `radioX` (зависит от ранее
  добавленной стабильной привязки MAC).
- При зависшем `rmmod`/ошибке поиска host — скрипт прерывается без
  отключения контроллера.
- Только после успешных ручных тестов можно обсуждать ограниченный
  автоматический recovery по конкретному событию AIC8800.

## Файлы

- `files/lib/aic8800.sh`: sysfs-поиск физического SDIO и UCI-радио.
- `files/usr/sbin/aic8800-recover`: ручное восстановление `--check|--run`.
- `.github/workflows/build.yml`: `chmod 0755` для утилиты в rootfs.
