# Cubie A5E — аппаратный план испытаний (A527, AIC8800D80)

Статус на **13 октября 2026**: есть два разных результата загрузки
Wi-Fi на той же microSD, подтверждены rootfs ext4 и стабильный PHY MAC,
но нет завершённого теста холодных запусков, ручного recovery, AP-клиентов
или эксплуатационной устойчивости.

Сначала читать [журнал расследования](AIC8800-SDIO-WIFI.ru.md) и
[инструкцию recovery](AIC8800-RECOVERY.ru.md). Этот документ — тестовый
протокол, а не утверждение, что проверки пройдены.

## Правила воспроизводимости

- Одна физическая плата: ревизия, производитель/объём DRAM и фото маркировки.
- Один образ и одна microSD на серию. Записать Git SHA, тип rootfs,
  DRAM-профиль, SHA256 образа, дату и источник питания.
- Не смешивать в одном A/B патчи MMC-frequency, power-sequence и UCI.
- UART или проводной Ethernet должны оставаться доступными, если тест
  предполагает `rmmod`, отключение MMC или reboot.
- **Не запускать recovery по Wi-Fi SSH**: соединение гарантированно
  прервётся при отключении радио.
- Если меняется MMC-нумерация — идентифицировать по физическому
  `4021000.mmc` (Wi-Fi) / `4020000.mmc` (SD-карта), а не по `mmc0`.

## 1. Идентификация и контроль загрузки

На каждом запуске:

```sh
date -Iseconds
cat /tmp/sysinfo/board_name
uname -a
cat /proc/mounts | grep ' / '
for h in /sys/class/mmc_host/mmc*; do
    echo "$h -> $(readlink -f "$h/device")"
done
dmesg | grep -Ei 'aic|sdio|mmc|pwrseq|firmware|timeout|EXT4' | tail -150
```

**Ожидается:** rootfs ext4 в `mmcblkXp2`, корректная DRAM, SDIO на
`4021000.mmc`. При наличии `aicwf_sdio_send_pkt fail-110` или
`bin upload fail` сохранить **полный** `dmesg` через UART/провод.

## 2. Независимая проверка физического Wi-Fi

```sh
for f in /sys/kernel/debug/mmc*/ios; do
    echo "=== $f ==="; cat "$f"
done
for p in /sys/class/ieee80211/*; do
    [ -r "$p/macaddress" ] || continue
    echo "phy: $p / mac: $(cat "$p/macaddress")"
    readlink -f "$p/device"
done
iw dev
```

На ранее удачном старте AIC8800 показывал **33,33 МГц actual**,
4-bit, 1,8 В, и `fc:23:cd:03:8e:78`. Это **контрольный эталон
данной платы**, а не MAC для прошивки всех плат.

Регистрировать три независимых признака:

1. SDIO-функция обнаружена на host.
2. Firmware загружена и появился PHY.
3. AP/STA действительно прошли передачу данных.

## 3. Конфигурация и скачущие radioX

```sh
uci -q show wireless
/sbin/wifi config
uci -q show wireless
wifi status
logread | grep -Ei 'hostapd|netifd|aic|wireless' | tail -100
```

**Ожидается после фикса `9d69e12`:** `radio0` распознаётся по MAC,
дубликаты старых путей `...mmc0:390b...` /
`...mmc1:390b...` не множатся. Не удалять пользовательские радио
автоматически по одному лишь индексу. Отдельно проверить
`wireless.default_radio0.disabled`: параметр должен отсутствовать
после uci-defaults, AP остаётся включённым.

**Тест миграции:** на свежем образе сделать одну успешную загрузку,
зафиксировать конфигурацию, затем `reboot` несколько раз и убедиться,
что SSID/настройки сохраняются при `mmcN` renumbering.
Добавить тест с USB Wi-Fi, если он есть: встроенное устройство должно
оставаться однозначно идентифицированным.

## 4. Тест AP и STA

- Для первого стендового теста — 5 ГГц, канал 36, HE80, реальная
  страна эксплуатации и разрешённый канал.
- Проверить `iw dev`, `wifi status`, `logread -e hostapd`,
  подключение телефона, получение IPv4 по DHCP и связь с LAN.
- Запустить `iperf3 -s` на плате и замер с клиента (10 мин,
  разнонаправленно). Записать пропускную способность, обрывы и лог SDIO.
- Отдельно: STA 2,4 ГГц, STA 5 ГГц, WPA2 и WPA3. AP+STA — только после
  подтверждения обоих режимов по отдельности.
- Встроенный лабораторный SSID `OpenWrt` без шифрования не использовать
  в открытой внешней сети. Перед эксплуатацией включить WPA2/WPA3.

## 5. Холодные старты и перезагрузки

| Серия | Количество | Признак прохождения |
|---|---:|---|
| Отключение / включение питания | 20 | SDIO → firmware → PHY → AP → клиент |
| `reboot` | 10 | Все этапы успешны, без лишних `radioX` |
| Перепрошивка с сохранением SD-профиля | 1+ | ext4 и UCI defaults работают |
| `sysupgrade` | 1+ | Только с резервной копией, без потери доступа |
| Нагрузочный AP/STA тест | 10 минут минимум | Нет зависаний / передачи с потерями |

`20/20`, `10/10` и отсутствие ошибок — **целевые критерии**. На
2026-10-13 эти серии не завершены.

Считать отдельно количество `-110`, успешных retry firmware и успешных
recovery. Никогда не скрывать количество ошибок за общим
«Wi-Fi есть».

## 6. Ручной SDIO recovery (пока не автоматизировать)

**Только через Ethernet/UART.** На **новом образе**, содержащем
`aic8800-recover`:

```sh
aic8800-recover --check
# Проверить физический host и отсутствие MMC block devices на нём.
aic8800-recover --run
logread -e aic8800-recover
dmesg | grep -Ei 'aic|sdio|4021000|error|timeout' | tail -120
iw dev
wifi status
```

Нужны три отдельных испытания:

1. Ручной recovery при исправном Wi-Fi — после выполнения должен
   вернуться PHY и AP, без изменения SD-карты и Ethernet.
2. Recovery **после настоящего** `-110`: зафиксировать, что SDIO
   перерегистрировался, firmware загрузилась и PHY вернулся.
3. Негативный сценарий: неправильный host, отсутствие `mmc-pwrseq`,
   `rmmod` отказал или завис — **запрещено** продолжать MMC
   `unbind`, скрипт обязан явно сообщить ошибку.

Есть блокировка параллельного вызова и максимум 3 попытки за 30 минут.
Не запускать цикл `while ... recover` и не добавлять procd/cron/uevent
до завершения всех ручных проверок.

## 7. Отдельные A/B гипотезы

| Гипотеза | Сравниваем | Статус |
|---|---|---|
| Снижение clock | DTS 35 МГц vs 25 МГц | не проведено |
| Power sequence | PM1 / WL_REG_ON, задержка после power-on | не проведено |
| Питание BLDO1 | текущий DTS vs вариант `regulator-always-on` Armbian | не проведено |
| Firmware wake-up | исходный драйвер vs инструментированный первый SDIO запрос | не проведено |
| Повторный MMC init | `rmmod/modprobe` vs unbind/bind MMC + modules | не проведено |

Изменять за один образ **один** фактор и фиксировать SHA.
Armbian использует 40 МГц, но это **не** доказательство, что
40 МГц устойчивы на нашем образе.

## 8. Что присылать вместе с результатом

```sh
{
    echo '=== build/system ==='
    date -Iseconds
    uname -a
    cat /tmp/sysinfo/board_name
    cat /proc/mounts | grep ' / '
    echo '=== mapping ==='
    for h in /sys/class/mmc_host/mmc*; do
        echo "$h -> $(readlink -f "$h/device")"
    done
    echo '=== wifi ==='
    uci -q show wireless
    iw dev
    wifi status
    echo '=== recovery ==='
    logread -e aic8800-recover
    echo '=== kernel ==='
    dmesg | grep -Ei 'aic|sdio|4021000|mmc|firmware|timeout' | tail -200
} > /tmp/cubie-a5e-test.txt 2>&1
```

Содержимое `/tmp` потеряется при reboot; заранее выгрузить
`/tmp/cubie-a5e-test.txt` на компьютер. Удалять персональные
данные/пароли/адреса WAN перед публикацией.

## 9. Gate перед beta

- Образы валидируются в GitHub Actions.
- 20/20 холодных запусков и 10/10 reboot.
- 0 невосстановимых firmware `-110`.
- Стабильная идентификация встроенного AIC8800 при перестановке MMC и
  наличии внешнего USB Wi-Fi.
- Ручной recovery испытан; нет побочных сбросов системной microSD.
- Клиент подключается к AP, получает DHCP, трафик идёт.
- Протоколы зафиксированы и привязаны к **одному SHA** сборки.
